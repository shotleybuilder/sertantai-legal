# Session: Issue #151: Concatenated Terms in Parser (CLOSED)

## Problem

247 rows (99 distinct patterns) have concatenated terms where multiple `<Term>` elements get joined into one — e.g. "highwayhighway authority", "commencecommencement", "validvalidity". The definition_list_strategy extracts multiple terms from the same list item but concatenates instead of splitting them. GH issue says 72 term pairs / 51 laws; session scoping found 247 rows / 99 patterns.

## Todo

- ✅ Investigate concatenated term patterns and root cause
- ✅ Fix term extraction to handle multi-term ListItems correctly (already works)
- ✅ Data cleanup of existing concatenated terms
- ✅ Run tests and diagnostic

## Dependencies

- ✅ Definition Bug Fixes Batch 5 (2026-08-19)
- ✅ Issue #148: Definition List Item Bleed (2026-08-19)

## Investigation

The current parser ALREADY handles paired/triple/quad terms correctly — `extract_via_term_element` returns a list of terms which `extract_definitions` maps over individually. Tested with 2-term, 3-term, and 4-term XML fixtures; all produce correct separate definitions.

The concatenated terms in the DB are stale data from a previous parser version. No code fix needed.

## Data Cleanup

Three-batch deletion:
1. **Batch 1** (247): Terms matching `([a-z]{3,})\1` — exact 3+ char repeat (e.g. "highwayhighway authority")
2. **Batch 2** (21): No-space terms > 15 chars with definition starting with separator (`, "` or `and "`)
3. **Batch 3** (62): Terms with definition starting with `and ""` pattern

Total: 330 concatenated definitions deleted. ~100 likely concatenated terms remain but are indistinguishable from legitimate long words (e.g. "decommissioning") without re-parsing. These will be fixed on next re-parse.

## Results

- 330 concatenated definitions deleted
- 60 tests pass (unchanged — no code changes needed)
- Diagnostic improved by 68: total 8,163 (was 8,231), term_not_found 1,843 (-36), no_citation 3,126 (-14), parent_unparsed 1,754 (-13)
