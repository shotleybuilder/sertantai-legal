# Session: Issue #162 geo_extent Resolution (ACTIVE)

## Problem

`geo_extent` mislabels devolved laws as `UK`. In-force Making laws: nisr 157, ssi 175, wsi 92, anaw 1, plus 136 ssi/wsi with null extent.

The scraper mixes four extent sources:
1. Law-level `@RestrictExtent`.
2. `ContentsItem/@RestrictExtent`.
3. Per-provision LAT `extent_code`.
4. Text clauses.

For **unrevised** documents, source 2 is a placeholder `E+W+S+N.I.` on every item, and the extent stage's "first ContentsItem" fallback lets it overwrite better values. Some revised laws are also simply stale.

Separately, **extent ≠ application**: `geo_extent` is extent only. Application is fractalaw's new field (#163).

Found by fractalaw's QQ session; full evidence in #162.

## Findings (2026-09-25)

- **Unrevised placeholder wins.** `staged_parser.ex` `parse_extent_xml` falls back to `//ContentsItem[1]/@RestrictExtent` whenever there's no law-level extent, and that is exactly the unrevised-document case, where every item carries the placeholder `E+W+S+N.I.`.
- **Stale revised laws.** The persister treats `geo_extent` and `geo_region` as "only set if nil" (`persister.ex` `@always_update_fields` excludes them). A corrected law-level extent from a later scrape never replaces an old `UK`.
- **`document_status` is parsed but never persisted** (`metadata.ex`).
- **The formats vary by source:**
  - `md_restrict_extent` keeps the raw form (`E+W+S+N.I.`, `N.I.`, and one `E+W+S+NI+i`).
  - LAT `extent_code` holds `E+W+S+NI`, `S` and `NI`, plus odd values like `E.W.` and `Scotland,Northern Ireland`.
  - `geo_extent` holds pan-region codes: UK 11,149, null 4,808, E+W 1,347, NI 995, S 868, GB 616, W 12, …
- **LAT extent clauses:** 215 laws.
  - Many also carry an application statement ("extend to England and Wales **and apply in England only**"). That part belongs to #163 and must not become extent.
  - Partial clauses ("Part 2 of this Act extends to Scotland—") must be ignored.

## Design (draft for Gemini review)

**`SertantaiLegal.Scraper.ExtentResolver`**, a pure module:
- `parse_regions/1`: any source format → a set of `England`/`Wales`/`Scotland`/`Northern Ireland`. It handles `+` and `.` separators, `N.I.`, full names and commas, and ignores unknown tokens.
- `pan_region/1`: regions → UK / GB / E+W / E+S / E / W / S / NI (the same outputs as today), else joined codes.
- `extent_clause/1`: LAT provision text → regions or nil.
  - Subject must be the whole instrument: "These Regulations", or "This Order/Act/Scheme/Measure/These Rules".
  - The extent phrase stops at "only", "and apply", "but apply" or sentence end.
  - A list continuation ("—") or "except"/"save" gives nil.
  - "United Kingdom" means all four nations; "Great Britain" means E, W, S.
- `resolve/1`, input `%{restrict_extent, document_status, lat_extent_codes, contents_item_extents, extent_clauses, type_code}` → `%{geo_extent, geo_region, source}`. The first source to give a verdict wins:
  1. `law_level`: `restrict_extent`, unless `document_status == "final"` (unrevised).
  2. `lat_provisions`: the union of non-empty LAT `extent_code`.
  3. `contents_items`: the union of ContentsItem extents, only when `document_status == "revised"`.
  4. `text_clause`: the union of whole-instrument extent clauses.
  5. `type_code` floor: ssi/asp/ssa → S; nisr/nia/apni/nisi → NI; wsi/anaw/asc/mwa → E+W.
  6. Otherwise nil. **Never `UK` by default.**

**Persistence:**
- New columns: `document_status` and `geo_extent_source` (additive).
- A resolved value with source S replaces the stored value when the stored source is null (legacy) or ranks no higher than S. An unresolved (nil) result never overwrites.

**Scraper:** the staged parser resolves after the metadata and extent stages, using the sources available at scrape time (law-level plus status, contents items, type code). LAT sources are used by `mix extent.resolve`, which is also the backfill.

**Backfill `mix extent.resolve`:**
- Dry run by default. `--apply` snapshots `geo_extent`, `geo_region` and `geo_extent_source` first.
- Sources come from the DB: `md_restrict_extent`, LAT `extent_code`, LAT extent clauses, type code. `document_status` is unknown, so law-level is accepted when present, and contents items are not used.
- Reports changes by (old → new, source), and specifically devolved laws that are still `UK`.

**Lints** (a mix task or part of the report): `type_code` vs `geo_extent`, and `geo_extent` vs the LAT union.

### Open questions

1. Unrevised uksi/ukpga laws with no LAT, no clause and no law-level extent currently read `UK` (the placeholder). They become **nil**. Is nil acceptable to compliance's jurisdiction exclusion (unknown means no exclusion)?
2. Should the LAT union outrank a law-level extent? LAT is per provision and could be narrower or wider than the law-level attribute.
3. Should a law-level extent be trusted when `document_status` is unknown (backfill)?

## Gemini review and decisions (2026-09-25)

Saved to `backend/data/code-reviews/2026-09-25-issue-162-geo-extent-design.md` (gemini-2.5-pro).

1. **Nil is acceptable and is better than a wrong `UK`.** Compliance must treat a nil `geo_extent` as unknown (no exclusion). Check this in its jurisdiction exclusion.
2. **Law-level stays above LAT.** Rejected Gemini's proposal to swap them: it assumed "LAT" meant an expert annotation source. The data: law-level and the LAT union agree for 564 of 571 laws (LAT wider for 4, narrower for 3). Our LAT is missing schedules for most laws (fractalaw QQ), so its union can be too narrow.
3. **Law-level is trusted when `document_status` is unknown** (backfill). `geo_extent_source` records the source.
4. **Text clauses are kept, but conservative.** Anything like "does not extend", "except", "save", "other than", "for the purposes of", or a list continuation ("—") gives nil. Crown dependencies are ignored. Only whole-instrument subjects count. (Gemini suggested cutting clauses altogether; they're rank 4, so they only decide laws with no law-level or LAT extent.)
5. **Explicit rank map in code:** `law_level` 1, `lat_provisions` 2, `contents_items` 3, `text_clause` 4, `type_code` 5.
6. **Write rule (accepted from Gemini):** a resolution, **including nil**, always overwrites a legacy value (`geo_extent_source` null). Otherwise a non-nil result overwrites only when its rank is equal or better, and nil never overwrites a sourced value. This clears the placeholder `UK`s, and a scrape-time resolve never undoes a LAT-based one.
7. **Re-resolve after LAT persist (accepted):** a hook in the LAT persister, so new LAT data updates extent without waiting for a backfill.
8. **Snapshot** only `id`, `geo_extent`, `geo_region` and `geo_extent_source`. Rollback is a documented SQL restore from the snapshot table.
9. **Lints are kept, but only as part of the dry-run report,** not as a separate task.

## Results (2026-09-25)

**Decision (Jason): keep unverified legacy values.** The first dry run under the "unknown overwrites legacy" rule would have cleared 5,854 `UK` values (5,627 uksi, 186 ukpga, …) and 67 non-placeholder `E+W`/`GB`/`NI`/`S` values. Instead, an unknown resolution never overwrites. `geo_extent_source = null` now means "legacy, unverified" and is treated as an upper bound.

**Applied** (11,158 UK laws):
- **Devolved corrections:** 1,266 `UK` → S, 910 `UK` → NI, 757 `UK` → E+W, 34 `UK` → GB.
- **~2,000 previously null laws** got a sourced extent.
- **Everything else** kept its value and now records its source.
