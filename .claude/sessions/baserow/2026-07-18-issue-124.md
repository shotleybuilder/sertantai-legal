Key correction: **Mix tasks are developer/operational commands, not runtime architecture.** With Oban already in place, `Node.connect` is unnecessary for single-node. ## Agent Codebase Research (2026-07-18)

Deep dive into the actual codebase settled the debate. Key findings:

### What already exists (Proposal C is 90% built)
- **27 mix tasks** all call `Mix.Task.run("app.start")` — full OTP tree
- **`SyncWorker`** already wraps `Engine.run/2` with retries, uniqueness, PubSub
- **`SchedulerWorker`** runs every 6h via Oban cron for due syncs
- **`SyncController.trigger_sync/2`** — HTTP endpoint already enqueues Oban job (`POST /api/sync/configurations/:id/sync`)
- **`--wait`/`--direct` flags** already exist on `mix sync.run`

### Zenoh suppression mechanism already exists
`application.ex:32-34` conditionally starts Zenoh:
```elixir
if(Application.get_env(:sertantai_legal, :zenoh)[:enabled],
  do: SertantaiLegal.Zenoh.Supervisor
)
```
Already `enabled: false` in `test.exs`. Just needs activation for mix task context.

### Recommended fix: auto-detect server mode
```elixir
defp server_mode? do
  Application.get_env(:sertantai_legal, SertantaiLegalWeb.Endpoint)[:server] == true
end
```
`mix phx.server` sets `server: true`; plain mix tasks don't. Use this to suppress Zenoh automatically — zero config, no env vars to remember.

## Multi-tenant future: DynamicSupervisor pattern (deferred)

For when we onboard customer #2 with concurrent sync needs:
- `Sync.DynamicSupervisor` — per-tenant worker lifecycle
- `Sync.TenantWorker` — crash-isolated GenServer with self-scheduling poll ticks
- `Sync.Registry` — process lookup by tenant_id (enables "Sync Now" button)
- `Sync.Orchestrator` — reconciles workers against DB on boot

Current Oban approach is fine for single-tenant. DynamicSupervisor doesn't preclude Oban — they complement each other.
