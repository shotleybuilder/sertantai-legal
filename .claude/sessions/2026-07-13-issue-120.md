## Data Migration Plan

### The problem
4,325 `legal_articles` rows have doubled section_ids (e.g. `reg.30(30)(2)` should be `reg.30(2)`). 63 of these laws also have `art.` instead of `reg.` on domestic instruments.

### How to distinguish wrong from correct
A `X(X)` pattern is **wrong** (P2 wrapper) when the provision has NO sibling with a different sub-number. If `reg.30` only has children `reg.30(30)`, `reg.30(30)(2)` etc — it's a wrapper. If `s.1` has children `s.1(1)`, `s.1(2)`, `s.1(3)` — those are legitimate subsections.

The sibling test: for the base ref (e.g. `reg.30`), search for any `reg.30(N)` where N != 30. If none exist, it's a wrapper.

### Three categories

1. **Standard doubles (4,206)** — rewrite: strip the first `(N)` where N matches provision. `reg.30(30)(2)` → `reg.30(2)`
2. **Double-doubled collisions (114)** — the target after rewrite is itself a doubled entry. Must migrate in dependency order: parents first (the wrapper P1 row moves out of the way), then children.
3. **True collisions (5)** — the target already exists as a legitimate P1 row (e.g. `reg.1(1)` → `reg.1` but `reg.1` already exists). The wrapper P2 row is a duplicate — delete it, don't rewrite.

### Migration steps

1. **Snapshot**: dump affected section_ids to a mapping table (`old_id → new_id → action`) for audit trail
2. **Delete 5 true-collision wrapper rows** — they're duplicates of existing P1 rows
3. **Rewrite parents first**: update rows where section_id matches `X(X)` exactly (no further suffix) — these are the wrapper P1 rows. `reg.30(30)` → `reg.30`
4. **Rewrite children**: update remaining doubled rows. `reg.30(30)(2)` → `reg.30(2)`. No collision now because step 3 moved the parent.
5. **Fix art.→reg. prefix**: for the 63 domestic laws, replace `art.` with `reg.` in section_id. Only for non-EU type_codes.
6. **Cascade to downstream tables**: update `control_mappings.section_id` and `amendment_annotations` using the same `old_id → new_id` mapping table
7. **Verify**: count doubled pattern — should be zero. Run control_mapping resolution check.
8. **Drop mapping table** after verification

### Safety

- Run in a transaction with explicit ROLLBACK point
- The mapping table is the audit trail — don't drop until verified
- NAS snapshot before migration
- All rewrites are deterministic regex — no ambiguity

## Data Migration Plan v0.2 — Re-parse and diff

v0.1 used regex heuristics to identify and rewrite corrupted section_ids. Gemini review flagged 8 risks including sibling test false positives, unchecked art.→reg. collisions, and missing downstream references. v0.2 eliminates most of these by using the fixed parser as the source of truth.

### Approach

Re-parse ALL laws (not just the 68 known-bad ones) with the fixed parser into a temp table, diff against existing data using a stable join key, build a corrections table, review, then apply. The parser is the authority.

### Join key: XML element id

The legislation.gov.uk XML assigns stable `id` attributes to each element (e.g. `id="regulation-30"`, `id="section-1-1-a"`). These don't change regardless of how we parse P2 wrappers. The parser now emits `xml_id` alongside `section_id` (internal field, not persisted to DB).

No schema change needed. `xml_id` is ephemeral — used only during migration:

1. Re-parse with new parser → temp table has `(xml_id, new_section_id)`
2. Walk same XML, look up existing `section_id` by position → `(xml_id, old_section_id)`
3. Join on `xml_id` → corrections table `(old_section_id → new_section_id)`
4. Apply corrections using `old_section_id` (the current PK)

### Scope: ALL laws, not just 68

Using XML element id as the join key requires re-parsing all laws, not just the 68 with known doubled section_ids. This is the right call:
- Other laws may have subtler issues the fix would correct (Gemini flagged this risk)
- A full re-parse gives us confidence in the entire LAT corpus
- The corrections table will show `no_change` for the vast majority — only genuine corrections are applied

### Steps

1. **NAS snapshot** before anything
2. **Modify parser**: emit `xml_id` (the legislation.gov.uk element id attribute) alongside section_id in the parse output
3. **Re-parse all laws into temp table**: run all ~450 laws through the fixed parser, write to `lat_reparse_temp` with columns `(law_name, xml_id, section_id, section_type, ...)`
4. **Automated sense checks**:
   - Row count per law: old vs new (new should be ≤ old — wrapper P2s removed)
   - Flag any law where new count EXCEEDS old (unexpected — investigate)
   - Flag any law where new count is <90% of old (large structural change — investigate)
   - Verify all new section_ids are unique within each law
5. **Build corrections table**: join `legal_articles` to `lat_reparse_temp` on `(law_name, xml_id)`. Output: `old_section_id → new_section_id → action (rewrite|delete|no_change)`
6. **Review corrections**: filter to `rewrite` and `delete` actions. Expected: ~4,325 rewrites + some wrapper P2 deletes. Any unexpected changes = investigate before proceeding
7. **Audit downstream references**: query information_schema for FK constraints on section_id. Grep codebase for soft references. Known:
   - `control_mappings.section_id`
   - `amendment_annotations.affected_sections` (text[] array containing section_ids)
   - `amendment_annotations.id` (contains section_id-like values)
   - Views or materialized views referencing section_id
   - Database triggers that fire on section_id changes
8. **Apply corrections in a single transaction**:
   - Disable FK constraints or update children first
   - Update `control_mappings.section_id` using corrections mapping
   - Update `amendment_annotations.affected_sections` array elements using corrections mapping
   - Update `amendment_annotations.id` where applicable
   - Update `legal_articles.section_id`
   - Delete wrapper P2 rows (action=delete)
   - Re-enable FK constraints if disabled
9. **Verify**:
   - Zero doubled section_ids remaining in legal_articles
   - No orphaned control_mappings or amendment_annotations
   - Control_mapping resolution rate against LAT
   - All section_ids unique within each law
10. **Apply same migration to production** using the same corrections table and process
11. **Baserow**: rebuild from scratch (full re-sync)
12. **Drop temp tables** after verification on both dev and prod

### Why this is safer than v0.1

- **No regex heuristics** — the parser decides what's correct, not pattern matching
- **No sibling test** — eliminated entirely, no false positive risk
- **Collisions visible in diff** — exact old→new pairs, detectable before applying
- **art.→reg. handled automatically** — the fixed parser produces correct prefixes
- **Stable join key** — XML element id from legislation.gov.uk, not derived values
- **Full corpus** — catches issues beyond the known 68 laws
- **Automated sense checks** — not manual spot-checks

### Risks (from Gemini review)

- **FK constraints**: must determine whether `ON UPDATE CASCADE` exists. If not, disable FKs or update children first. Check for triggers on affected tables.
- **xml_id availability**: need to verify all elements have stable ids (most do — legislation.gov.uk assigns them consistently). Elements without ids (e.g. some SignedSection) need fallback matching.
- **Performance**: re-parsing ~450 laws and diffing ~97K rows. Should be manageable in minutes, but needs the XML cached locally (or fetched in batch).
- **Rollback**: single transaction for all DB changes. If it fails, ROLLBACK reverts everything. NAS snapshot as belt-and-braces.
