### Model B decision: two independent family signals

**Decision**: `family` and `enacted_families` are semantically independent columns.

| Column | Meaning | Set by |
|---|---|---|
| `family` | What is this law *about*? (intrinsic subject) | SI code mapping + title keywords |
| `enacted_families` | What families does it *enable*? (extrinsic, derived) | Aggregated from child law families |

**Why**: Acts fall into three tiers by enacted_families breadth:
- 370 single-family specialists (e.g. Animal Health Act → 228 children, all ANIMALS)
- 145 domain-anchored (2-5 families, dominant at 60-70%+, e.g. HSWA → OH&S 65%)
- 23 general-purpose enablers (6+ families, e.g. European Communities Act → 46 families, 1241 children)

Forcing `family` to match `enacted_families` is wrong — general enablers (ECA, EU Withdrawal Act)
are correctly `🖤 No Family` because they're constitutional machinery, not domain law.
Domain Acts like EPA are correctly `ENVIRONMENTAL PROTECTION` even though they also enable WASTE, WATER etc.

**Rejected alternatives**:
- Model A (strip family, use enacted_families only): loses intrinsic subject identity, breaks filtering
- Model C (auto-promote dominant enacted family): circular — child families determine parent, parent used to infer children

**Secondary laws that enact (110 parents)**:
- 54 are NI Orders in Council (_nisi_) — effectively primary legislation for Northern Ireland.
  Behave like Acts: domain-specific, highly coherent (94/110 have single-family children).
- 48 are UK SIs (_uksi_) — unusual. One major outlier: EC (Designation) Order 1972 (12 families,
  183 children) mirrors ECA as a general enabler. The rest are domain-specific.
- Should be treated with higher suspicion in QA — a true SI-enacts-SI is rare and may indicate
  a wrong enacted_by link. When correct, expect tight family coherence.

**SI code as cross-validation signal**:
- Parent's OWN si_code (not enacted_si_codes which is derived from children) provides an
  independent signal. 69% of parents have no usable own si_code (NULL, empty, or `["[]"]`).
- Where it exists: models.ex maps SI codes → families. This can cross-validate the parent's
  `family` assignment independently of enacted_families.
- For children: child SI code can be mapped to family via models.ex and compared against
  the child's assigned `family` — a mismatch there is a real signal of wrong family assignment.
- Three-way cross-check possible: child.family vs models(child.si_code) vs parent.enacted_families
  distribution — disagreement on any axis is worth flagging.

**QA implications for Enacted By tab**: The old mismatch concept (child.family ≠ parent.family)
is meaningless under Model B. `enacted_families` is derived FROM child families, so a child's
family is always present by definition. The real QA questions become:

1. **Link validity**: Is this enacted_by link correct?
   - Secondary (SI) parents are higher suspicion than primary (Act) parents
   - NI Orders (_nisi_) are expected; other SI types less so
   - Re-parse button lets operator verify by re-extracting from legislation.gov.uk XML

2. **Outlier within enacted_families distribution**: Does this child's family stand out
   against siblings? e.g. 1 TRANSPORT child among 236 AGRICULTURE children is suspicious.
   Could be wrong enacted_by link OR wrong child family assignment.

3. **SI code cross-validation**: Does models.ex(child.si_code) agree with child.family?
   If not, either the SI code mapping or the family assignment is wrong — independent of
   the enacted_by relationship.

4. **Unclassified children**: Parents with children but empty enacted_families (207 parents)
   — the children lack family assignment, so the aggregate can't populate.

### Rich SI code ↔ family mapping (replace models.ex many-to-one)

**Problem**: models.ex maps 156 of 630 SI codes (25% coverage), each to exactly one family.
Reality is many-to-many — `ENVIRONMENTAL PROTECTION` appears across 31 families, `HEALTH AND SAFETY`
across 20. Current emoji-domain grouping (💙/💚/💜) for SI mismatch rule creates new edge cases
for cross-domain topics (nuclear, pesticides).

**Data shape** (SI codes with 5+ laws):
- 33 SI codes map cleanly to 1 family
- 71 SI codes span 2-3 families (avg dominant 76%)
- 70 SI codes span 4-10 families (avg dominant 60%)
- 13 SI codes span 10+ families (avg dominant 46%)

**Reverse-fill opportunity**: 1,239 laws have family but no SI code (661 pre-2000, the
legislation.gov.uk gap era). A good mapping could infer SI codes from family assignment.

**Approach**: Derived `si_code_families` table, rebuilt from scratch alongside law_edges.

```
si_code_families (PK: si_code, family)
  si_code     text      -- e.g. "SEEDS"
  family      text      -- e.g. "💚 PLANT HEALTH"
  law_count   int       -- laws with this pairing
  pct         numeric   -- % of laws with this SI code having this family
```

~630 SI codes × ~5 families avg ≈ 3-4k rows. Rebuilt by mix task (full drop + reinsert).

**Guard against circular reinforcement**: The table is always derived, never hand-edited,
never used as a write-through authority. It surfaces patterns for QA ("this looks unusual"),
never constrains ("this is wrong"). Fixing a law's family on uk_lrt and rebuilding propagates
the correction into the map. The raw numbers are visible in the UI so operators can judge
whether the statistical pattern is trustworthy or reflects a systematic misclassification.

### Claude skill: Enacted By parser QA

**Problem**: The enacted_by parser (`enacted_by.ex`) extracts parent law references from
legislation.gov.uk introduction XML via pattern matching (SpecificAct, PowersClause,
FootnoteFallback). It produces incorrect links — e.g. "Employers' Liability (Compulsory
Insurance) (Amendment) Regulations" linked to "Offshore Installations and Pipeline Works
(Management and Administration) Regulations" instead of the Employers' Liability Act.

**Approach**: A Claude Code skill that systematises AI-driven QA of enacted_by links.

Workflow:
1. **Sample** — pull suspect enacted_by links from the graph tab (outliers, SI-enacts-SI,
   or random sample from the full 8,441 edges)
2. **Fetch** — retrieve the actual introduction/enacting formula text from legislation.gov.uk
   XML (same source data the parser uses)
3. **Verify** — Claude reads the enacting text and judges whether the parsed parent is correct,
   using text + contextual signals (title similarity, SI code, family coherence)
4. **Classify** — wrong link | correct link | ambiguous | parser limitation (e.g. footnote
   resolution failed, wrong Act matched from multiple references)
5. **Feedback loop** — patterns in parser failures (e.g. "always picks first footnote instead
   of the enabling Act") inform targeted improvements to `enacted_by.ex` pattern matching

The skill builds a structured log of verified/rejected links that measures parser accuracy
and prioritises fixes to the parsing logic itself. Incremental — run it against batches,
fix the parser, re-run to measure improvement.

- [ ] Run QA batches against outlier + SI-enacts-SI populations
- [ ] Use findings to improve enacted_by.ex pattern matching strategies

### Remove linked_* columns — use source columns directly

**Finding**: `linked_enacted_by` and the other 4 `linked_*` columns are stale partial copies
of `enacted_by`, `amending`, `amended_by`, `rescinding`, `rescinded_by`. The schema says they
are `🧮_derived` from the source columns but the derivation step was never built. Same format
(`UK_type_year_number`), no transformation needed.

**Impact of the gap**:
- `law_edges.rebuild` reads `linked_*` columns → misses 1,561 enacted_by relationships
  that exist in `enacted_by` but not in `linked_enacted_by`
- 229 laws where `linked_enacted_by` and `enacted_by` point to DIFFERENT parents
  (e.g. UK_uksi_2008_1765: linked has wrong parent, enacted_by has correct one)
- 7,416 of 7,839 (95%) are identical — confirming they're the same data, just stale

**Database check**: No views, triggers, or functions reference `linked_*` columns.
