### Silent Staleness Risk from Content Digest Gate — Major
- Where: Proposed items (3), Alternatives considered (Staleness B), Risks and limits
- Finding: The core architectural choice for staleness detection (Item 3: "A downstream stage re-runs when an upstream stage's output changes, by its content digest, not when upstream code changes") carries a significant risk of silent staleness. If a code change (e.g., a bug fix, an improved algorithm) in an upstream stage alters the *logic* but does not produce a different *content digest* for the *currently processed data*, then downstream stages will not re-run. This directly violates Goal 2 ("No stored record can be out of date without `lat.stale --strict` saying so") and the context's emphasis on correctness ("wrong labels are worse than slow builds"). The rejected alternative B (per-law dependency tracking) was dismissed for "missed dependency means silent staleness," but the chosen approach risks a similar outcome when logic changes are not reflected in existing data's output digests. The mitigation "run one full rebuild comparing digests after the split" is a one-time check, not a continuous safeguard against future logic changes.
- Fix: Revisit the staleness strategy for code changes in stages. Introduce an explicit "stage code version" for each stage's logic. If a stage's code version changes, invalidate its cache and re-run it and all downstream stages for affected laws, irrespective of content digest. The content digest comparison would then primarily be used to detect changes in *input data* or to prevent unnecessary re-stamping if a code change happens to produce identical output for a specific law.

### Catalogue Cache - Risk of Missing Code-Logic Changes — Major
- Where: Proposed items (4), Alternatives considered (Catalogues C)
- Finding: Item 4 proposes caching catalogue results keyed by "the file's digest and the catalogue's version". Similar to the issue with stage splits, if the *logic* of the catalogue generation itself changes (e.g., a bug fix in how `feed patterns` are extracted), but the `catalogue's version` (which is implied to be a static module version, not a content hash of the code) does not change, and the input file's digest has not changed, the cache will serve a potentially stale result. This would violate Goal 2.
- Fix: Ensure the "catalogue's version" used in the cache key is explicitly derived from the *content digest of the catalogue code* (e.g., a SHA-256 of the relevant Elixir module(s) and their dependencies). This way, any change in the catalogue's logic will invalidate the cache for that catalogue, forcing a re-run for affected files.

### Reliance on Process for Rebuild Frequency — Major
- Where: Proposed items (1)
- Finding: Item 1 proposes "Batch edits, rebuild once (a rule)" to control rebuild frequency. While the addition of a `--stale` option is good, relying on a "rule" for when to rebuild earlier families is a process-based solution to a technical problem. Human discipline is prone to error and does not scale well. The problem statement itself highlights how manual processes currently lead to excessive rebuilds ("four full rebuilds in one step"). While Item 3 (split version by stage) is the technical solution, Item 1 still frames a manual orchestration of rebuilds as a primary control mechanism.
- Fix: Clarify that Item 3 (split version by stage with content-digest/code-version gates) is the *primary* technical mechanism to reduce rebuild frequency. Item 1's "batch edits, rebuild once" should be rephrased as a desirable consequence or best practice *enabled* by the technical solution, rather than a standalone rule to manage a system flaw. The system should ideally automate the identification of what needs rebuilding based on code and data changes, rather than requiring manual `lat.stale --list` followed by a hand-crafted `mix lat.vocabulary --build --laws ...`.

### Open Questions Recommendations

**1. Item 3 before Environmental Protection, or after it? Recommendation: before.**
**Recommendation:** Before.
**Justification:** The problem statement clearly highlights the growing cost and frequency of full rebuilds ("four full rebuilds in one step at about 14 min each"). Environmental Protection is a large family ("395 live laws, 59 with rows today"), and processing it *before* implementing item 3 would exacerbate the existing problem, leading to unnecessary and lengthy rebuilds for earlier families with every code change during its development. Implementing item 3 first directly addresses the core scalability and staleness issues, making subsequent family integrations more efficient and less error-prone. The architectural risks identified in the review (e.g., silent staleness from content digests) need to be mitigated, but the general principle of stage-gating is sound for efficiency.

**2. Should item 1's rule go into `RULES.md` now?**
**Recommendation:** No.
**Justification:** Item 1, "Batch edits, rebuild once (a rule)", is a procedural workaround for a technical limitation that Item 3 aims to solve. Placing a process rule into `RULES.md` *before* the underlying technical solution (Item 3) is implemented and proven stable risks codifying an inefficient or error-prone workflow. Once Item 3 is implemented and effectively reduces the need for full corpus rebuilds, the *need* for such a manual rule might diminish or change significantly. A refined process, reflecting the new capabilities and automated staleness detection, could then be documented.
